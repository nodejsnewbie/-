# 单人协作框架 v0.1

> **定位**：本文件把 [`AGENTS.md`](../AGENTS.md) 为「多人团队」写的角色分工、7 步开发法与红线规则，**折叠**成一个人 + AI 编码代理可每天执行的节奏。它**不新增红线、不改口径**，只回答一个问题——**当所有角色都由一个人（借助 AI）承担时，怎么保证纪律不塌。**
> **版本**：v0.1｜**适用范围**：`apps/admin` · `apps/technician` · `apps/user` · `services/server` · `services/ai` · `packages/shared` 全部工作区
> **前提约束**：本文所有验收/红线动作沿用 [`AGENTS.md`](../AGENTS.md) 原文，冲突时**以 AGENTS.md 为准**并回填修正本文。

---

## 0. 为什么会有一份「单人协作框架」

AGENTS.md 定义了 7 个研发角色（PM / 需求分析 / 技术负责人 / 前端 / 后端 / 测试 QA / 运维 SRE）+ 1 个 AI 编码代理，并假设它们由**不同的人**担任，靠「角色之间的制衡」来兜底：QA 拥有一票否决、技术负责人书面批准例外、PM 冻结验收口径。

单人项目里这层制衡**天然不存在**——写代码、判对错、批例外、宣布验收「过了」，可能都是同一个人在同一个瞬间决定。这正是单人 + AI 项目的最大风险：**自律会疲劳，制衡会退化成一言堂，而 AI 会忠实地执行你带病的那个决定。**

因此本框架的核心不是「怎么分工」（就一个人），而是**用「时间上的角色切换」和「机械闸门」把团队里本该存在的制衡补回来**。三条主轴：

1. **人与 AI 的分工边界**——哪些必须你拍板，哪些可交给 AI，以及 AI 产出如何验收（重度 AI 参与版）。
2. **单人多角色轮值流程**——一个人如何按 7 步开发法轮流戴不同帽子，每次换挡的强制检查点。
3. **Git 与提交/PR 节奏**——一个人也要走分支、走 PR、走机械合并门禁，把 PR 当成「给未来的自己和 AI 的交接文档」。

## 1. 一页速查（先记这一屏）

| 时刻 | 你戴的帽子 | 这一步只做什么 | 不可跳过 |
| --- | --- | --- | --- |
| 接到需求 | PM / 需求分析 | 判定是否属「待客户确认」范畴，先入 §4 隔离带 | 不把假设当事实写进代码（R4/R5/R6/R7） |
| 动手前 | 技术负责人 | 冻结本次变更的验收口径（一句话 GWT + 跑哪些命令算过） | 写进 PR 描述，先定标准后写码 |
| 写码中 | 开发（指挥 AI） | 按 §2 边界派活给 AI，人做设计与裁决 | 新增代码合规（存量违规不豁免新代码） |
| AI 交回 | 开发 | 逐行读 diff，理解每一处才提交 | 不提交自己没读懂的代码 |
| 提交前 | 测试 QA（换帽子） | 跑机械闸门：`lint`→`lint:eslint`→`build`→（动后端）基线+smoke | 见 §3.3 / §5 |
| 收尾 | 技术负责人 + QA | 对照红线自查 + 对照冻结口径验收；例外书面记 PR | 违反任一 R1–R10 = 本次失败，禁止「先上后补」 |
| 合并 | 运维 SRE | 走 PR 自审 → 合并；push 前确认没带 `dist`/`.env`/密钥 | 见 §6 |

## 2. 人与 AI 的分工边界（重度 AI 参与）

你的日常是：**AI 写码 + 改文档，你做决策与验收。** 这条边界不是「AI 能不能写」，而是「谁对结果负责」。原则一句话：**AI 负责产出，人负责判断；判断权不下放。**

### 2.1 决策权归属表

| 事项 | 谁拍板 | AI 的角色 |
| --- | --- | --- |
| 需求优先级 / MVP 范围 / 验收口径 | **你（PM）** | 可起草 PRD 段落，但口径由你定稿 |
| 技术选型 / 契约冻结 / 红线例外 | **你（技术负责人）** | 提供方案对比；例外须你书面写进 PR |
| 「这个结论算不算事实」 | **你** | AI 不得自行把待确认假设当事实实现 |
| 具体实现（组件、接口、SQL、脚本） | AI 主导 | 在冻结契约内自由实现，交回你评审 |
| 「测试过了没有」 | 机械闸门 + **你（QA 帽子）** | AI 可跑命令，但**不得宣布「需求完成」**（AGENTS 注意事项 5、14） |

> AI 编码代理**无红线豁免权**（AGENTS 注意事项 14）。它满足不了红线时必须如实上报失败，禁止放宽校验、跳过测试或伪造通过证据。你在派活时要把这句显式写进任务，别默认 AI 会守。

### 2.2 交给 AI vs 必须自己做

**可放手让 AI 做（低风险、可机械验证）**：模板/样板代码、类型定义补全、按现有 pattern 加 CRUD 路由、批量格式化、写测试骨架、文档草稿、跑基线脚本抓 diff、把响应逐字比对。

**必须你自己做（判断、担责、不可外包）**：

- 定义「做完长什么样」（GWT 验收口径）——这是团队的 PM/QA 职责，折叠到你身上。
- 判定某结论是不是「待客户确认假设」——只有你能区分事实和假设（AGENTS 前提状态）。
- 金额、权限、合规、溯源这类红线相关逻辑的**最终裁决**（AGENTS 注意事项 10：前端可即时反馈但不能作最终判定；单人项目里「最终判定」就是你看代码确认）。
- 读 AI 的每一行 diff 并理解——**不理解就不提交**（见 §3.3）。

### 2.3 AI 产出的验收闸门

AI 交回的任何改动，在你（开发帽子）读 diff → 你（QA 帽子）跑闸门之前，视为**未验证草稿**。闸门顺序固定（命令口径见 AGENTS「常用命令」）：

```bash
npm run lint          # R1 类型门禁，全工作区 tsc --noEmit，必须 0 error
npm run lint:eslint   # 代码质量（未用变量/显式 any/hooks），0 error（2 个有意 warn 除外）
npm run build         # R2 构建，全工作区 exit 0，无未捕获异常
```

**动了后端接口 / 数据层时追加**（AGENTS「迁移规则」：改结构必须留回归证据）：

```bash
# 改结构/迁移前后各抓一次基线，逐字节比对
node scripts/capture-api-baseline.mjs   # 改前 + 改后各一次（core / mall profile）
node scripts/compare-api-baseline.mjs   # 必须 0 处不一致
node scripts/smoke-mutations.mjs        # 写操作与错误形状断言全过
```

**动了 `services/ai` 时追加**：`pytest`（不依赖真实密钥的契约测试）。

> ⚠️ 单人踩坑点：**闸门是机械的，不是感觉**。`npm run build` 曾出现「tsc 认为已是最新、一个文件不产出却报成功」的静默失败（AGENTS 历史坑）。所以要看命令**退出码和实际产物**，别只看「没报错」。不要让管道吞掉退出码（AGENTS 注意事项 15）。

### 2.4 例外与红线的处理

单人没有「技术负责人书面批准」这道他人审批。补法：**把例外写进 PR 描述当作给自己和未来的审计痕迹。** 格式固定：

```
【红线例外】R<编号>：<要豁免的具体点>
理由：<为什么本次必须豁免>
补偿措施：<本次用什么替代把关，如手工核对清单>
复核：<已复核 / 待复核 + 复核人=你自己 + 日期>
```

无书面记录的例外视为未获批 → 触发 R10 变更纪律。

### 2.5 待确认需求的隔离带（关键前提）

AGENTS 反复强调：第 3 步的「确认」全部是**开发方判断、未经客户确认**，是待验证假设。**这是本项目当前最高优先的未知量，单人 + AI 模式下尤其危险**——AI 会把你含糊的假设当成明确需求忠实实现。

规则：

- 涉及 R5（资质纯人工）、R6（窜货/熔断不做）、R7（分红口径）的口径，在客户答复前，**AI 提示词里必须显式标注「这是待确认假设，不得据此宣布完成、不得对外承诺」**。
- 这类内容落进代码/界面时，用 Mock 必须显式标注为 Mock（R4、注意事项 5），且**不得流入生产**。
- 需要向客户发问时，走 [`docs/requirements/discovery-questions.md`](requirements/discovery-questions.md) 的第一层 7 题，**上一层不确认不问下一层**；未答复的进 §7 阻塞登记，不靠猜继续。

## 3. 单人多角色轮值流程

### 3.1 角色折叠表

AGENTS 的 7 个研发角色 + AI，在单人项目里折叠成「你 + AI」两方，你的帽子随时间切换：

| 原角色 | 折叠到 | 什么时候戴这顶帽子 |
| --- | --- | --- |
| PM | **你** | 每次开工定义范围与验收口径时 |
| 需求 / 业务分析 | **你** | 把模糊需求转成 GWT、识别是事实还是假设时 |
| 技术负责人 | **你** | 冻结契约、判定红线、批准（自己的）例外时 |
| 前端 / 后端开发 | **你指挥 + AI 产出** | 实现阶段 |
| 测试 / QA（一票否决） | **你（必须隔离于开发时刻）** | 提交前跑闸门、宣布验收时 |
| 运维 / SRE | **你** | 提交、push、PR、合并、发布判断时 |
| AI 编码代理 | **AI** | 所有产出性工作，无红线豁免权 |

### 3.2 与 7 步开发法的映射（单人版）

AGENTS「开发流程」的 7 步，单人下不必逐天走完，但**每步的产出物必须有**。当前进度见 AGENTS「当前进度」表，卡点在**第 3 步待客户确认**——第 4 步 PRD 未定稿前，本框架下的开发只碰「结构搬移 / 已冻结契约内 / 不承诺需求完成」的活。

1. 环境准备 → 已完成（AGENTS 进度表）。
2. Skill 准备 → 已完成。
3. 需求探讨 → **产出完成但待客户确认**，按 §2.5 隔离。
4. PRD + 契约/数据模型冻结 → 每次开工前你补「本增量的小 PRD + GWT」，落到 §5 任务记录。
5. UI 风格 → 沿用现有 `index.css` `@theme` token 真源（AGENTS 代码规范·样式）。
6. 前后端并行（你 + AI）→ 前端 AI 可自出、你评审；后端改动必走基线/烟测（§2.3）。
7. 测试驱动验收 → 你（QA 帽子）跑页面体检 + 四类接口校验（契约/合规/权限/资金，AGENTS 第 7 步扩写）。

### 3.3 换挡检查点（补回制衡的关键）

**核心动作：写完代码的「开发你」，和判对错的「QA 你」，必须是分开的两个时刻。** 连写带审最容易放水。最低要求：

- **作者 → 评审者隔离**：AI 或你写完一段后，**不要立刻自评**。把闸门和 diff 阅读放到「下一步」，最好隔一个短停（哪怕 10 分钟或先去做别的），再回来以「这是别人写的、我要挑毛病」的姿态读。
- **逐行读 diff**：提交前 `git diff --staged`（或等价）逐行读。不理解每一行为什么这么写，就不提交——这既是对 AI 产出的把关，也是对未来的自己的保险。
- **红线自查清单**：验收时对照 R1–R10 逐条问「本次是否触发」（速查表见 AGENTS 红线规则）。触发任一 = 判定失败，禁止合并。
- **口径先于实现**：动手前一句话写清 GWT 与「跑哪些命令算过」（AGENTS R9 要求 GWT 100% 通过），写进任务记录或 PR 草稿，避免边写边挪标准。

### 3.4 一个功能的最小产出物（单人也不省）

一次可交付增量应同时留下：代码 + 对应的类型/契约同步（R3）+ 后端改动的基线证据（若有）+ PR 描述（含验收口径与例外记录）+ §7 状态更新。缺项 = 未完成。

## 4. 单人如何对待「测试失败判定权」

AGENTS 把「测试失败判定权、可否决合并」交给 QA。单人的你既是被告也是法官，唯一不塌的办法是**把判定标准前移成机械规则 + 事前书面口径**：

- 判定标准**事前**就写好（§3.3），事后只对照，不临场放宽。
- 「过了」= 闸门命令的真实退出码 0 **且** 逐字节基线 0 不一致 **且** GWT 全通过 **且** 未触发红线——四个条件缺任一即为「没过」。
- 拿不准时默认判「没过」，把疑点写进 §7 阻塞登记，而不是说服自己放行。

## 5. Git 与提交/PR 节奏（单人也要走流程）

一个人不等于可以裸提交。分支和 PR 的价值，在单人 + AI 项目里是**把「决策—实现—验收」留痕，给未来的自己和 AI 当交接文档**。

### 5.1 分支模型（够用即可，别过度）

| 分支 | 用途 | 命名 |
| --- | --- | --- |
| `main` | 稳定可发布基线，只接受经 PR 合并的改动 | — |
| `feat/<域>-<短描述>` | 功能 / 界面增量 | `feat/amoeba-settlement-split` |
| `fix/<域>-<短描述>` | 缺陷修复 | `fix/dispatch-distance-label` |
| `refactor/<域>-<短描述>` | 纯重构（行为不变） | `refactor/admin-feature-split` |
| `chore/...` `docs/...` | 依赖、格式化、文档 | `chore/upgrade-prisma` |

小改动（改个文案、加个注释）可直推 `main`，但**一旦触及逻辑/接口/数据，必须走分支 + PR**。

### 5.2 提交规范

沿用 AGENTS「代码规范·提交」：Conventional Commits，**一个提交只做一件事，重构与功能变更不得混合**。建议正文附一行「依据」，方便未来追溯。

```bash
# 例
git commit -m "$(cat <<'EOF'
feat(amoeba): 工单分别记录服务净值与农资金额

依据 R7 口径（分红基数 = 服务净值 × 档位系数）；拆分原型单一 settlementAmount。
验收：npm run lint/build exit 0；后端基线 core 15/15 无回归；smoke 全过。
EOF
)"
```

> push 前必查：**不带 `node_modules`/`dist`/`.env`/密钥**（R10）。确认没把真实手机号/身份证/证件原件进仓库，须脱敏 `138****7819`（R4）。

### 5.3 PR 即交接文档（自审）

单人项目里 PR 不是给别人看的，是给**下周的你**和**下次接手的 AI 会话**看的。每个 PR 描述固定含四段：

1. **做了什么 / 为什么**（一句话业务动因，链到 §7 任务或需求文档）。
2. **验收口径（事前写的 GWT）+ 实际闸门结果**（贴 `lint`/`build`/基线/smoke 的真实结论与退出码，注明「Mock 环境」）。
3. **红线自查**（R1–R10 逐条「未触发 / 触发说明」）。
4. **例外记录**（若有，用 §2.4 格式）。

合并走「自审 → 合并」，但**自审要在与编写分开的时刻做**（§3.3）。

### 5.4 机械合并门禁（不可省的清单）

合并前逐条打勾（任一不过禁止合并，对齐 AGENTS 红线「禁止先上后补」）：

- [ ] `npm run lint` 全工作区 exit 0，无新增未说明的 `@ts-ignore`/`as any`/隐式 any（R1）
- [ ] `npm run lint:eslint` 0 error（R1/代码质量）
- [ ] `npm run build` 全工作区 exit 0，无未捕获异常（R2）
- [ ] 改了接口：`types` + `services/server` + 全部调用方同步；无已发布字段破坏性变更（R3）
- [ ] 动了后端：capture→compare 0 不一致 + smoke 全过（迁移规则）
- [ ] 数据无 Mock 落库、敏感信息已脱敏（R4）
- [ ] 合规/权限/资金/溯源相关：最终判定在服务端，未被降级为仅前端/仅提示（R5/R7/R8/R6）
- [ ] 未提交 `node_modules`/`dist`/`.env`/密钥；无单文件 > 500 行（R10）
- [ ] 若涉「待客户确认」口径：已标为假设 + Mock 标注，未宣布完成（§2.5）

## 6. 日常节奏与会话交接

### 6.1 节拍

- **一天开工**：先看 §7 状态 → 定今天 1–3 个可验证小增量 → 每个先写 GWT（技术负责人帽子）。
- **一天收工**：跑一遍闸门 → 未完成的写进 §7 → 有进展的提交。保持工作区可编译，别让「半成品堆到第二天」。

### 6.2 上下文交接（重要，单人 + AI 频繁换会话）

本项目重度依赖多轮 AI 会话。会话切换会丢上下文，用三样东西把状态持久化：

- **§7 状态区**（本文末尾或单独维护）：当前在做什么、卡在哪、下一步。
- **handoff skill**（可用技能列表里有 `handoff`）：长任务告一段落时，主动「保存进度 / 会话交接」，让下一次会话能续上。
- **PR / 提交信息**：最可靠的「为什么」留痕（§5.2 的「依据」行）。

### 6.3 待办与阻塞登记

「待客户确认」是最大的挂起项。用统一清单管理，避免靠记忆：

| 状态 | 条目 | 处置 |
| --- | --- | --- |
| ⏸ 阻塞（待客户） | 第 3 步全部结论（R5/R6/R7 口径） | 走 discovery-questions 第一层 7 题；答复前不定稿 PRD、不对外承诺 |
| 🟡 待办 | `apps/technician` 真机验证、`apps/user` 存量缺陷整改 | 见 AGENTS「已知遗留」 |
| ✅ 已冻结可动 | 结构搬移、契约内实现、格式化、文档 | 本框架下正常推进 |

## 7. 落地待办（本框架自身的下一步）

1. 你确认本框架口径后，可把 §7 状态区抽成独立 `docs/STATUS.md` 单独维护（本文件先内联）。
2. 若后续接入 CI（CNB 流水线 / Vitest / Playwright，AGENTS「质量工具」标 ❌ 未接入），§5.4 的门禁清单从「手动跑」升级为「流水线强制」。
