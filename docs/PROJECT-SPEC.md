## 4. 角色权限边界与决策权

| 角色              | 关键权限边界                                           |

## 5. 目录组织原则与现状

### 5.1 组织原则

1. **按业务域组织，不按技术类型平铺**——目标是「删掉一个业务模块时能一次性删干净」。
2. **数据访问单入口**：所有 HTTP 调用集中在 `src/services/`。
3. **类型单真源**：领域类型只在 `src/types/`，跨端共享。
4. **一级 Tab 一个入口文件**：侧边栏每个菜单项对应一个视图文件。
5. **通用组件与业务组件分离**：`components/` 放无业务通用件，业务件随 feature 走。

## 6. 开发流程明细

### 6.1 七步法的本项目裁剪（含后端环节）

本项目遵循 **CC 全流程指南的 7 步开发法**，并按本项目「核心风险在后端」的现实做了两处扩写（**不新增步骤编号**）。

> 指南原文面向 Claude Code，称项目宪法为 `CLAUDE.md`、技能目录为 `.claude/skills/`；本项目实际使用 DSH（DeepSeek Harness），等价采用 `AGENTS.md` 与 `.dsh/skills/`——**仅命名不同，方法不变**。

| 步骤 | 命名         | 本项目扩写                                                                                                                                                         |
| ---- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | 环境准备     | 技术栈选型 + 创建项目 + 安装依赖 + 编写项目宪法 `AGENTS.md`                                                                                                        |
| 2    | Skill 准备   | 4 个 Skill 安装到 `.dsh/skills/`（真源，入库）                                                                                                                     |
| 3    | 需求探讨     | 由 agent 扮演产品经理主动追问，产出产品定义卡片 + 信息架构                                                                                                         |
| 4    | PRD 编写     | 分文档模式 `docs/0_index.md`、`1_common.md`、`2_pc_*.md`、`9_data_dict.md`；**并扩写为「需求 + 接口契约与数据模型」**——同时冻结 OpenAPI 契约、领域模型、状态迁移表 |
| 5    | UI 风格确定  | 生成 3 套 HTML demo 方案 → 团队投票选定 → 封装 `ui-design-system` Skill                                                                                            |
| 6    | 前端开发     | 按 P0→P1 逐页面开发（每页对照对应 `2_pc_*.md`）；**并扩写为「前后端并行开发」**——后端按已冻结契约实现                                                              |
| 7    | 测试驱动验收 | `testai` 做页面体检；**并扩写验收范围**——追加接口契约校验、合规路径校验、权限越权校验、资金计算校验                                                                |

### 6.4 核心状态机（验收依据）

**工单（`WorkOrder`）** —— `currentStep` 1→5：

```text
1 pending_dispatch  待调度/算力匹配中
      │  派单（dispatchOrder）
      ▼
2 dispatched        已派工 · 正在赶赴现场
      │  到场打卡（updateOrderStep 3；写入 watermarkVerified / watermarkTime / watermarkGps）
      ▼
3 checked_in        现场打卡完成
      │  开具电子处方（updateOrderStep 4；生成 prescriptionCode）
      ▼
4 prescription_issued  电子处方已开具
      │  农户签字验收（updateOrderStep 5；写 signedAt / settlementAmount）
      ▼
5 completed         已验收结单
```

异常分支：`exception`（接单超时预警），可从任一环节进入，需紧急改派。

**资质审核（`AuditApplication`）**：

```text
pending ──approve──▶ approved ──▶ 技师 dispatchStatus = active（进入可派单池）
   │
   ├──reject────▶ rejected
   └──revision──▶ revision（退回补正，等待重新提交）
```

**阿米巴结算（`AmoebaSettlement`）**：`pending → cleared`（`processing` 为中间态），`cleared` 时写 `bankClearedAt`。

> 三条状态机是 R5 / R7 / R9 的判定基准：绕过审核直接 `active`、或跳过打卡直接开方，一律判定失败。

### 6.5 需求变更流程

1. 提出变更 → 记录到 `docs/requirements/` 的变更记录；
2. 评估影响面（契约、状态机、测试用例、已发布功能）；
3. 技术负责人 + PM 确认后更新 PRD 版本号与需求状态；
4. **同步更新测试用例**；未更新用例的变更不得进入开发。
