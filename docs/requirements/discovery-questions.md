# 需求探讨提问计划（分层推进）

> **沟通方式**：微信、讨论阶段。**不发问卷、不让客户填表、不要求一次答完。**
> **节奏**：一次只问一层，每层 2–3 题，答完再往下。上一层不确认，不问下一层。

---

## 0. 上一版问卷为什么不合适（留档，避免重犯）

| 问题         | 说明                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| 分层维度错了 | 按**面谈对象**分层（决策层 / 财务 / 合规 / IT）——这是**审计或访谈排期**的视角，不是**讨论阶段**的视角 |
| 题量错了     | 65 题＋20 条假设登记表，微信发不出去，客户也不会填                                                    |
| 姿态错了     | 「请确认或纠正我方理解」适合方案评审，不适合刚开始聊需求——这个阶段客户自己也没想清                    |

**改法**：按**需求深度**分层。第一层只聊「为什么做、为谁做、现在怎么做」，不碰任何细节规则。

## 1. 分层路线图

| 层         | 主题             | 要定下来的事                                           | 状态          |
| ---------- | ---------------- | ------------------------------------------------------ | ------------- |
| **第一层** | **需求本质**     | 真实痛点、使用者、现状流程、业务范围、首版目标、硬约束 | 👈 **现在做** |
| 第二层     | 业务范围与主流程 | 每类服务各自怎么跑、三个端各干什么、角色怎么配合       | 待第一层确定  |
| 第三层     | 规则与算法       | 资质怎么审、派单怎么匹、分红怎么算、结算怎么走         | 待第二层确定  |
| 第四层     | 数据与集成       | 字段、编码规则、与外部系统对接                         | 待第三层确定  |

> 第四层之后才轮到技术实现。**现在讨论地图要不要做、用不用 OCR，都为时过早**——那些是第三、四层的事。

## 2. 第一层：需求本质（7 题，现在问这些）

> 每题给出：**怎么问**（口语版，可直接发）｜**为什么问**｜**会影响什么**

### A 组：为什么做、给谁做（建议先发这 3 题）

---

**Q1 最痛的那件事**

- **怎么问**：这个平台要做的事挺多。如果只能先解决一件，您最想解决哪件？
- **提示方向**（只用来帮客户打开思路，不要替他选）：技师管不住 / 农户找不到服务 / 服务响应慢 / 产品卖不动 / 应付检查压力大 / 上面看不到数据
- **为什么问**：这一题决定后面所有优先级。MVP 选什么、看板放什么，都由它推出来
- **会影响**：北极星指标、MVP 范围、第一版工期

---

**Q2 谁用、谁拍板**

- **怎么问**：平台上线后，除了您，还有哪位同事会天天看这个后台？
- **为什么问**：一是信息架构（几个角色、每个角色看什么），二是**确认以后需求找谁定**
- **会影响**：角色与权限设计；后续所有需求的确认人

---

**Q3 现在没有系统是怎么做的**

- **怎么问**：现在农户想找人上门打药，是怎么找到技师的？服务完之后谁记一笔？钱怎么结？
- **为什么问**：**这是本层最有价值的一题**。现状流程是唯一不会骗人的需求来源——客户说「我想要什么」常常不靠谱，说「现在怎么做」基本准确
- **会影响**：能一次性推翻我们此前的很多猜测（见 §5）

---

### B 组：做成什么样（建议第二批发这 4 题）

---

**Q4 平台要做哪几类服务**

- **怎么问**：上门服务除了打药，还包含哪些？比如飞防、农机维修、土壤检测、送农资，这些做不做？
- **为什么问**：划定业务范围；也顺带验证我们猜的「5 类」对不对
- **会影响**：工单类型、技师资质匹配、农户端报单表单

---

**Q5 第一版先跑到哪**

- **怎么问**：如果先上一个版本，您希望它先把哪一段跑通？（比如先能把技师和资质管起来，还是先能把农户下单、派单跑通）
- **为什么问**：MVP 边界。**注意别问成「都要不要」——客户一定说都要**
- **会影响**：MoSCoW、页面开发顺序、工期

---

**Q6 什么算做成了**

- **怎么问**：一年以后，您觉得这个平台做到什么样子，就算没白做？
- **为什么问**：定成功标准。纪要里有「扩大辐射范围、提高服务响应影响力」，但那是方向，不是标准
- **会影响**：目标与验收口径、看板指标

---

**Q7 硬约束**

- **怎么问**：有没有时间上的硬要求？有没有检查、监管上的硬要求（比如农药经营许可证那块）？预算上有没有上限？
- **为什么问**：约束决定方案。合规硬要求尤其重要——它可能直接否掉一些功能设计
- **会影响**：范围、合规红线、排期

---

## 4. 纪要里已经有的，不要重复问

上次的会议纪要已经明确说过的，**别再问一遍**（会显得没做功课），但可以顺着追问一层：

| 纪要已有                                   | 不要问           | 可以追问                                   |
| ------------------------------------------ | ---------------- | ------------------------------------------ |
| 三端：企业端 / 技师端 / 农户端             | 「要做几个端」   | 「三个端里，哪个最先上？」                 |
| 农药经营许可证是最关键资质                 | 「要不要管资质」 | 「现在谁在管？多久审一次？过期了怎么办？」 |
| 一物一码溯源、市场监管合规上货             | 「要不要溯源」   | 「现在赋码是怎么做的？有没有上报要求？」   |
| 阿米巴模式、让新农人成股东                 | 「要不要做分红」 | 「现在分成是怎么发的？有没有成文规则？」   |
| 地图定位因年费暂不做                       | 「要不要做地图」 | 不用问，已明确                             |
| 诉求：扩大宣传辐射范围、提高服务响应影响力 | 「目标是什么」   | 「这两个方向，哪个更急？」                 |
| 30 多个产品销量上不来                      | 「为什么做平台」 | 「服务做好了，销量的转化您预期怎么发生？」 |

## 5. 第一层答完后的验证动作

第一层的答复会**直接检验开发方此前的猜测**。拿到答案后，优先核对这 5 条（它们牵连的文档最多）：

| 猜测                                    | 出处       | 若被推翻，要改               |
| --------------------------------------- | ---------- | ---------------------------- |
| 服务范围 5 类                           | 开发方判断 | 工单类型、资质匹配、报单表单 |
| 首版交付三端、不含商城                  | 开发方判断 | MoSCoW、页面清单、工期       |
| 后台仅 2 个角色（运营管理员、区域督导） | 开发方判断 | 权限矩阵、页面可见性         |
| 单县试点、30–50 名技师                  | 开发方判断 | 性能设计、指标口径           |
| 分红仅来自服务收入                      | 开发方判断 | 结算公式、成本模型           |

> 完整假设清单仍在 [`client-confirmation-questionnaire.md`](client-confirmation-questionnaire.md)（**该文件降级为内部备查，暂不发给客户**）。

## 6. 本层不用问客户、我们自己能定的

避免把内部决策也丢给客户：

- 技术栈（React / NestJS / PostgreSQL / Taro）——内部技术选型
- 目录结构、代码规范、红线规则——内部工程约定
- 用不用 OCR、要不要人脸核身——**先问「现在资质怎么审」，客户答完自然知道有没有 OCR**，不要直接问技术手段
- 地图 API 采购——已明确不做，二期再议

## 7. 下一层的触发条件

**第一层 7 题都有答复后**，才进入第二层（每类服务各自怎么跑、三端分工、角色配合）。

若第一层只答了一部分：**只追未答的那几题，不要跳到第二层**。跳层的代价是拿到一堆无法归位的细节。
